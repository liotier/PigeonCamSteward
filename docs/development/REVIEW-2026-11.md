## Part 1 - answerable now

### Q1. Retry a failed rotation automatically, and how hard ? (A4)

- **For.** One transient failure currently costs a ~23.5 h broadcast,
  double the ceiling the project exists to respect, unless a person
  reacts to a single notification.
- **Against.** Each API attempt inserts a broadcast and spends roughly
  300 quota units. Unbounded retries every 30 minutes would spend about
  14,400 units a day against a default allowance of 10,000, and litter
  the channel with abandoned "upcoming" entries.
- **Recommendation.** Retry at 5, 10, 20, then every 30 minutes, capped at
  6 attempts per rotation interval; notify on the first failure and on
  giving up; pair with the stale-broadcast cleanup in [A10](#a10-rotation-closes-the-old-broadcast-before-the-new-one-exists). Confirm or
  amend those numbers.

### Q2. Remove the in-process snapshot output now ? (F4)

- **For.** It is documented as harmful, off by default, and already
  superseded on paper by `design/frame-freeze-from-segments.md`. Its
  ffmpeg arguments, config block, watchdog branch and tests are carried
  for no user.
- **Against.** Deleting it before the replacement exists removes the only
  camera-side stuck-picture detection, even if nobody can safely enable
  it; and it removes the test bed for the unverified audio-queue theory.
- **Recommendation.** Delete now, implement the segment-based design as
  its own piece of work. The theory can still be tested from git history.

### Q3. An opt-in retention cap for the archive ? (B5)

- **For.** Usage grows by `daily_archive_gb` every day without bound; the
  disk filling is a certainty with a date, and at that point recording
  stops silently.
- **Against.** The spec declines to enforce a storage budget, and
  automatic deletion of irreplaceable footage is the most dangerous thing
  this project could do by default.
- **Recommendation.** Add `archive.max_age_days`, empty by default (no
  deletion ever happens unless the operator writes a number). The alerts
  in [B5](#b5-the-archive-can-stop-silently) are independent of this answer and should be built either way.

### Q4. Move the timer intervals out of the unit files ? (F3)

- **For.** Two values exist in two places and a doctor check exists
  solely to detect their drift; the rotation timer already shows the
  cleaner pattern.
- **Against.** It works, drift is detected, and the values rarely change.
  The watchdog key would be removed from config - a small break.
- **Recommendation.** Low value; do it only after [F1](#f1-load-the-configuration-once-per-process), or not at all.

### Q5. Adopt GitHub Actions for CI ? (E1)

- **For.** The suite is the project's gate and currently runs only when
  someone remembers; a missing linter passes silently.
- **Against.** A hosted dependency and its maintenance, for a
  single-maintainer project; the runner's ffmpeg and systemd versions
  will differ from the deployment's.
- **Recommendation.** Accept. Free for public repositories, and the
  `.deb` build job would have caught [D2](#d2-libpigeoncam-usbresetpy-is-never-installed).

## Part 2 - answerable after a manual test

### Q6. Insert the new broadcast before closing the old one ? (A10)

- **For.** Today a failure at insert or bind (quota, a 5xx outliving the
  retries, a network fault) leaves the channel with no live broadcast
  until the external check climbs its restart ladder to `--recover`.
  Moving the insert ahead of the close confines such a failure to "the
  rotation did not happen" - the existing broadcast keeps running. Only
  the position of one call changes; bind, restart and the transitions keep
  their order.
- **Against.** `SPEC.md` §5.4.1 numbers the close as step 1, and the
  current order is the one validated on the real channel. A second
  broadcast in `created` state coexisting with a live one is ordinary API
  usage (that is what a scheduled event is), but it has not been exercised
  by this project.
- **Recommendation.** Accept, conditional on manual test
  [M6](#manual-test-m6-insert-before-close-on-a-real-channel-a10). The spec's
  *sequence of transitions* is preserved; record the deviation the same
  way the `testing` hop already is.

**This answer depends on one manual test.** Until it is run, the recommendation stands on the API documentation alone.

#### Manual test M6. Insert-before-close on a real channel (A10)

Needs: the channel and API credentials. One rotation with the reordered
sequence while a broadcast is live: confirm the insert is accepted, the
old broadcast completes, the new one reaches `live`, and viewers on the
`/live` URL follow. Then confirm `liveBroadcasts.delete` removes a
deliberately abandoned `upcoming` broadcast.

### Q7. May the external check match yt-dlp's error text ? (A3)

- **Context.** Observed during this review: yt-dlp exits 1 with no JSON
  for an upcoming event, and its source raises an error for a channel
  with nothing live. The check calls both "indeterminate" and never acts.
- **Option a - structured only.** Add `--ignore-no-formats-error` and
  classify on the JSON `live_status` field. Covers the upcoming /
  "Preparing stream" case. Does not cover a channel with nothing
  scheduled at all, which produces no JSON under any flag.
- **Option b - a plus a narrow stderr match** for the no-JSON case. The
  spec warns against parsing human-readable output, rightly: a wording
  change would silently alter behaviour. Mitigation: unrecognised text
  stays indeterminate, so a wording change degrades to today's behaviour,
  never to a restart storm.
- **Option c - a plus the YouTube API** (`liveBroadcasts.list` on the
  current id, one quota unit) where API access is configured. Fully
  structured, but leaves deployments without API access where they are.
- **Recommendation.** a + b + c together. Refusing b means the default,
  credential-free deployment cannot detect "the channel is simply not
  live" at all, which is the first thing an external check should detect.

**This answer depends on one manual test,** already partly done. Case 1 decides whether option b is needed at all: if a channel with nothing scheduled yields JSON under the second command, option a suffices and no text matching is required.

#### Manual test M1. yt-dlp output when the channel is not live (A3)

Needs: any machine with yt-dlp and network for case 1; your own channel
and encoder for cases 2 and 3. Run both commands in each case and keep
stdout, stderr and exit status as fixtures:

```bash
yt-dlp -j --no-warnings --no-playlist "https://www.youtube.com/@HANDLE/live"; echo "exit=$?"
```

```bash
yt-dlp -j --no-warnings --no-playlist --ignore-no-formats-error "https://www.youtube.com/@HANDLE/live"; echo "exit=$?"
```

1. A channel with nothing live and nothing scheduled.
2. Your channel with a broadcast sitting at "Preparing stream".
3. Your channel a minute after a broadcast ended.

Already observed in this review (yt-dlp 2026.10.26, a public channel with
an event scheduled two days ahead): the first command exits 1 with empty
stdout and `ERROR: [youtube] <id>: This live event will begin in 2 days.`;
the second exits 0 with JSON carrying `"is_live": false,
"live_status": "is_upcoming"`. Case 1 is expected, from the source, to
fail under both commands with "The channel is not currently live".

### Q8. Ship the watchdog fix before it has run on real hardware ? (A1)

- **For.** The escalation is unreachable today, so the fix cannot make
  the hung-camera case worse than "restart forever".
- **Against.** It activates a hardware action - a USB power cycle or
  rebind - that has never executed in production from this code path. A
  mistake in the new window logic would reset a healthy camera.
- **Recommendation.** Merge with the simulation-based tests; before the
  next season run [M2](#manual-test-m2-watchdog-escalation-end-to-end-a1-b1) once. If
  that cannot be done first, deploy with `watchdog.usb_reset.cooldown_seconds`
  raised (for instance 3600) for the first weeks.

**This answer depends on one manual test.** It is the only way to learn whether the escalation, once reachable, behaves on the real hub and camera.

#### Manual test M2. Watchdog escalation end to end (A1, B1)

Needs: the camera, the hub, the real units. With the stream running:

```bash
sudo kill -STOP "$(systemctl show -p MainPID --value pigeoncam-stream.service)"
```

Expected in `journalctl -u pigeoncam-watchdog -f`: one `STALL_RESTART`,
which clears the stall (a stopped process is replaced). To exercise the
escalation the fault must survive the restart: unbind the camera's driver
or use a hub port that can be powered off, so ffmpeg opens the device and
receives nothing. Expected: `STALL_RESTART`, then `USB_RESET_ESCALATION`
at the following stall, then frames resuming. Record which reset method
succeeded and how long the device took to reappear.

### Q9. Drop privileges for yt-dlp and remote-media ffmpeg calls ? (C1)

- **For.** A self-replacing binary parsing remote web content, and ffmpeg
  decoding remote media, run as root while needing only network access.
  The spec's requirement that units run as root is untouched: only
  individual child processes change identity.
- **Against.** One more moving part (`setpriv`), and yt-dlp may want a
  writable cache directory that `nobody` lacks, which is how a "harmless"
  hardening change blinds a health layer.
- **Recommendation.** Accept, with a fallback to the direct call plus one
  WARN, and only after [M8](#manual-test-m8-unprivileged-yt-dlp-and-ffmpeg-c1).

**This answer depends on one manual test,** which does not need the deployment host - any machine with yt-dlp, ffmpeg and root will do, so it can be run now.

#### Manual test M8. Unprivileged yt-dlp and ffmpeg (C1)

## How to use this document

- Items are ordered by priority within each section, and sections are
  ordered by how directly they affect the project's purpose (an unattended
  stream that stays up and stays under YouTube's archive ceiling).
- **Evidence** says how the finding was established:
  - *Verified* - reproduced in this review by running the real code.
  - *Read* - established by reading the code; not executed.
  - *Inferred* - depends on the behaviour of an external system (YouTube,
    yt-dlp against a real channel, real hardware) that could not be
    exercised here. Confirm before fixing.
- The [working agreements](README.md#working-agreements) apply to every
  item: test first and watch it fail, `SPEC.md` stays untouched, config
  changes update `config.example.yaml` + `tests/lib/fixtures.sh` +
  `tests/test_config_schema.sh` together, user-visible changes update
  `docs/TROUBLESHOOTING.md`.
- Items marked **decision needed** change behaviour the maintainer chose
  deliberately, or touch the frozen spec's sequence. Do not implement them
  until the matching question in
  [Decisions awaited](#decisions-awaited-from-the-developer) is answered.
- Everything that needs a camera, real systemd units or a real YouTube
  channel is collected in
  [section M](#m-what-requires-a-live-system), with a table saying which
  items can be finished without it - except the five manual tests a
  decision depends on, which sit with their question in Part 2 above.

## A. Defects in the core recovery paths

### A1. The USB-reset escalation cannot be reached

**Where:** `bin/pigeoncam-watchdog.sh:254` (the `else` branch resetting
`stall_restart_count=0`), `bin/pigeoncam-stream.sh:94` (progress file
truncated on every start), `tests/test_watchdog.sh` (stall #2 scenario).

**Problem.** The escalation fires when a stall is detected while
`stall_restart_count >= escalate_after_restarts`. The counter is reset to
zero by any check that is not stalled. After a restart, `pigeoncam-stream.sh`
truncates the progress file, which gives it a fresh mtime. With the shipped
30 s interval and 60 s timeout, the first check after the restart always
sees `age < stall_timeout` and an empty frame counter, classifies that as
healthy, and resets the counter - whether or not ffmpeg ever produced a
frame. A permanently hung camera therefore produces `restart, reset,
restart, reset, ...` forever and never a USB reset.

**Evidence (verified).** A simulation with a fake `systemctl` whose
`restart` truncates the progress file (what the real service does), and no
frames ever written:

```
check 1: STALL_RESTART            stall_restart_count=1
check 2: (not stalled)            stall_restart_count=0
check 3: STALL_RESTART            stall_restart_count=1
check 4: (not stalled)            stall_restart_count=0
...                               uhubctl calls: 0
```

The existing test passes because it hand-writes a stale progress file
between two watchdog runs, a state the real system cannot be in after a
restart (see [E2](#e2-two-fakes-model-states-the-real-system-cannot-produce)).

**Proposed fix.** Reset the counter only on positive evidence of recovery,
not on absence of evidence of a stall:

1. Treat a check as "recovered" only when the frame counter is non-empty
   **and** greater than zero **and** different from the previous check's
   value. Anything else after a stall restart is "pending": neither
   increments nor resets.
2. Persist `last_stall_restart_epoch`. A stall detected within a window of
   the previous stall restart (suggest `2 * stall_timeout + 2 *
   check_interval`, no new config key) counts as "the restart did not clear
   it" regardless of the intermediate pending checks.

**Tests.** Give the fake `systemctl` an opt-in mode that truncates the
progress file on `restart`, and rewrite the escalation scenario on top of
it: (a) hung forever -> escalates on the second stall; (b) restart then
real frame progress -> counter resets; (c) the existing cooldown scenario
still holds.

### A2. A crash-looping stream is invisible to every health layer

**Where:** `bin/pigeoncam-watchdog.sh:150` (the `is-active` gate),
`systemd/pigeoncam-stream.service` (`Restart=always`, `RestartSec=10`,
`StartLimitIntervalSec=0`, no `OnFailure=`).

**Problem.** When ffmpeg exits immediately on every start (camera node
gone, device busy, a bad option after a config edit, an invalid stream
key), the unit alternates between `activating (auto-restart)` and a
few seconds of `active`. Consequences:

- The watchdog either returns at the `is-active` gate or sees a progress
  file that was truncated seconds ago, so it never reports a stall and
  never escalates to a USB reset - although "camera fell off the bus" is
  the case the reset exists for.
- `pigeoncam-failure-notify@` is deliberately not wired to the stream unit.
- The external check reports not-live only if [A3](#a3-channel-not-live-is-probably-classified-as-indeterminate)
  is fixed, and then answers with more restarts.

Net effect: an indefinite outage with no notification from any layer.

**Proposed fix.** In the watchdog, before the `is-active` gate, read
`systemctl show -p NRestarts,ActiveState,SubState pigeoncam-stream.service`
and keep the previous `NRestarts` in the state file:

- `ActiveState=inactive` (deliberate stop, rotation gap): unchanged
  behaviour, return.
- `NRestarts` grew by at least N (suggest 3) since a check that last saw
  frame progress, and no frame progress since: log `STREAM_CRASH_LOOP`,
  call `notify_escalation` once per threshold (same re-arming shape as
  `note_indeterminate`), and feed the same escalation ladder as a stall
  when `camera.device` does not exist.

**Tests.** Extend the fake `systemctl` with a `show` verb driven by
environment variables; scenarios for deliberate stop, crash loop with the
device present (notify only), crash loop with the device missing (notify
and USB reset), and recovery.

### A3. "Channel not live" is probably classified as indeterminate

**Where:** `lib/pigeoncam-common.sh:621-643` (`fetch_live_json`),
`bin/pigeoncam-status-check.sh:400-456`, `tests/fixtures/fake-bin/yt-dlp`
(`not_live` mode).

**Problem.** The three-way classification treats "yt-dlp exited 0 with
JSON saying `is_live: false`" as confirmed-not-live and any non-zero exit
as indeterminate. In yt-dlp 2026.10.26:

- A channel `/live` URL with nothing live raises `UserNotLive`
  ("The channel is not currently live") in
  `yt_dlp/extractor/youtube/_tab.py` - an error, exit status 1, no JSON.
- An upcoming or "Preparing stream" broadcast goes through
  `raise_no_formats(reason, expected=True)` in
  `yt_dlp/extractor/youtube/_video.py`, which also raises unless
  `--ignore-no-formats-error` is passed.

So the two states the external check exists to catch most likely arrive as
"indeterminate", which by design never acts. The only consequence would be
the `EXTERNAL_CHECK_BLIND` notice after 20 polls (about an hour), whose
wording tells the operator the stream "may be fine". The doctor already
hints at this: its own probe says a failed extraction "may just mean not
currently live" (`bin/pigeoncam-doctor.sh:285`). No `confirmed NOT live`
event appears anywhere in `INCIDENTS.md`; every field `EXTERNAL_RESTART`
recorded there came from the frozen-picture check.

**Evidence.** yt-dlp source read directly, and one of the two cases
observed against the real service (below). The fake's `not_live` mode is
an assumption nobody recorded from the real tool.

**Partial confirmation obtained in this review.** Against a public
channel with an event scheduled two days ahead, the project's exact
command exited 1 with empty stdout and
`ERROR: [youtube] <id>: This live event will begin in 2 days.`; with
`--ignore-no-formats-error` it exited 0 with JSON carrying
`"is_live": false, "live_status": "is_upcoming"`. The upcoming case is
therefore established: the current check calls it indeterminate. The
remaining cases need [M1](#manual-test-m1-yt-dlp-output-when-the-channel-is-not-live-a3).

**Decision needed** on the stderr match below - see
[Q7](#q7-may-the-external-check-match-yt-dlps-error-text--a3).

**Fix.**

1. Add `--ignore-no-formats-error` and classify on the JSON `live_status`
   field (`is_live`, `is_upcoming`, `was_live`, `post_live`, `not_live`)
   instead of `.is_live // false`.
2. For the channel-level case that yields no JSON at all, capture stderr
   and classify a small, explicitly listed set of yt-dlp messages as
   confirmed-not-live. The spec discourages matching human-readable text,
   and for good reason; the mitigation is to keep the patterns in one
   function, test them against the recorded real outputs, and let anything
   unrecognised remain indeterminate, so a wording change degrades to the
   current behaviour rather than to a restart storm.
3. Where YouTube API access is configured, cross-check with
   `liveBroadcasts.list(id=<current_broadcast_id>, part=status)` - one
   quota unit, structured, no text matching. This is the `method: api`
   alternative that `fetch_live_json` currently rejects as unimplemented.

**Tests.** Replace the fake's `not_live` mode with modes that replay the
recorded outputs byte for byte.

### A4. A failed rotation is not retried for a full interval

**Where:** `bin/pigeoncam-rotate.sh:52` and `:110` (marker written before
the attempt), `:170-213` (`check_rotation_due`), and the `--force` help
text, which documents the consequence.

**Problem.** `last_rotation_at` serves two purposes: the start of the
grace window for the external check, and the age that decides whether a
rotation is due. It is written before the attempt so the grace window
covers the gap. When the attempt fails (expired token, a transient API or
network error, `systemctl` failure), the marker still says "just rotated",
and the 5-minute timer declines every run for the next 11h45m. One
transient failure therefore doubles the broadcast length to roughly 23.5
hours unless a person reacts to the single `ROTATION_FAILED` notification.

**Proposed fix.** Split the two meanings:

- `rotation_attempt_at` (durable): written before each attempt; the
  external check's rotation grace reads this.
- `last_rotation_at` (durable): written only when the rotation succeeded;
  `check_rotation_due` reads this.
- `rotation_failures` (durable counter): a failed attempt increments it;
  the next timer run retries once `min(5 min * 2^failures, 30 min)` has
  elapsed since `rotation_attempt_at`. Notify on the first failure and then
  every Nth, not on every retry. Success resets it.
- In api mode a retry after a partial failure must run with `--recover`
  semantics (discover what is actually bound), since the first attempt may
  already have completed the old broadcast.

**Tests.** `tests/test_rotate.sh`: failed api rotation followed by a timer
run 6 minutes later retries; a run 1 minute later does not; success
clears the counter; the external check's grace follows the attempt marker.
Mind the migration: an existing deployment has only `last_rotation_at`.

### A5. Nothing serialises the actors that restart the stream

**Where:** `bin/pigeoncam-rotate.sh` (timer-driven),
`bin/pigeoncam-status-check.sh:270` (`systemd-run ... pigeoncam-rotate.sh
--force`, a transient unit distinct from `pigeoncam-rotate.service`, so
systemd does not deduplicate them), the watchdog's and the status check's
own `systemctl restart`.

**Problem.** A forced rotation launched by the border check can overlap a
scheduled one; two API rotations interleaving would each close the other's
new broadcast. The watchdog can restart ffmpeg in the middle of an API
rotation's wait for `streamStatus=active`. Grace periods cover the common
timings but are not a lock.

**Proposed fix.** `flock -n` on `/run/pigeoncam/rotate.lock` around the
body of `pigeoncam-rotate.sh` (exit 0 with an INFO line when held). The
watchdog and status check test the same lock non-blockingly and skip any
*action* while a rotation holds it; observation and state updates still
run.

**Tests.** Hold the lock from the test, run each script, assert no
`systemctl` action verb is logged.

### A6. Status-check loses state on the backoff exit path

**Where:** `bin/pigeoncam-status-check.sh:461-464`.

**Problem.** The "still not live; backing off" branch exits without
`write_state`. Mutations made earlier in the same run are lost:
`last_frame_sample_at` and the frozen counters set inside
`check_frame_freeze`, and the `consecutive_indeterminate=0` reset. While a
freeze is in backoff, every 3-minute poll therefore fetches a fresh frame
instead of honouring `check_interval_seconds` - the over-sampling that
`note_sample_failure`'s own message warns can provoke YouTube into
refusing the fetch.

**Proposed fix.** Call `write_state "$state_path"` before that `exit 0`.
Better: install a single `trap 'write_state "$state_path"' EXIT` once the
state has been read, and delete the scattered calls.

**Tests.** Frozen + backoff active: run twice, assert the fake ffmpeg was
invoked once.

### A7. Archive trim can cut a segment that is still being written

**Where:** `bin/pigeoncam-archive-trim.sh:172-180` (only the current hour's
prefix is skipped).

**Problem.** Segments are named by start time. With
`archive.segment_length_seconds` above 3600 (or any value that does not
divide the hour), a segment that started in a previous hour is still open
when the trim runs at `:05`, and is trimmed, replaced by `mv`, or deleted
under ffmpeg. `pigeoncam-reencode.sh` already guards against this with an
mtime check; the trim does not, and nothing validates the setting.

**Proposed fix.** Skip any file modified within the last 120 seconds
(reuse `progress_age_seconds`, as the re-encode script does), and have the
doctor WARN when `3600 % segment_length_seconds != 0`.

Also: `pigeoncam-archive-trim.service` sets `ProtectHome=true`. An
`archive.segment_dir` under `/home` makes the directory invisible to the
trim, which then logs "does not exist, nothing to trim" forever. Add a
doctor FAIL for a segment directory under `/home`, `/root` or `/run/user`.

### A8. YouTube API list calls read only the first five results

**Where:** `api/rotate_via_api.py:567-571` (`discover_current_broadcast_id`)
and `:659-664` (`sweep_stray_broadcasts`).

**Problem.** `liveBroadcasts.list` defaults to `maxResults=5`
([reference](https://developers.google.com/youtube/v3/live/docs/liveBroadcasts/list)).
Neither call sets it or follows `nextPageToken`. With more than five
active broadcasts (the pile-up the sweep exists to clean), strays are
missed and discovery can fail to find the bound broadcast.

**Proposed fix.** `maxResults=50` and a `pageToken` loop in a small shared
helper. Add a mocked two-page test to `tests/test_youtube_api.py`.

### A9. Network errors bypass the API script's retry and error handling

**Where:** `api/rotate_via_api.py:409-424` (`_with_retry` catches only
`HttpError`), `:290-301` (token refresh catches only `RefreshError`),
`:591-593` (`subprocess.run(check=True)`), `:823-833` (`main` catches only
`HttpError`).

**Problem.** A DNS failure, connection reset or socket timeout raises
`httplib2.ServerNotFoundError`, `OSError`/`TimeoutError`, or
`google.auth.exceptions.TransportError`. None is retried, and all escape
`main` as a raw traceback - the outcome the file's own comment says must
not happen "on the one path that runs unattended at 3am". A brief network
blip at rotation time currently fails the rotation outright, which
[A4](#a4-a-failed-rotation-is-not-retried-for-a-full-interval) then turns
into a 23-hour broadcast.

**Proposed fix.**

- Retry transport-level exceptions in `_with_retry` with the same bounded
  backoff. Also retry HTTP 403 when the error reason is
  `rateLimitExceeded` or `userRateLimitExceeded`.
- Wrap the token refresh in the same retry for `TransportError`.
- Catch `subprocess.CalledProcessError` from `restart_stream`.
- A final `except Exception` in `main` that logs one labelled line with
  the exception type and exits 1.

Minor, same file: `main` tests `cfg(config, "youtube_api.enabled", False)`
rather than `cfg_bool`, so a quoted `"false"` is truthy (`:805`);
`bool(made_for_kids)` has the same problem with a quoted value (`:449`).

### A10. Rotation closes the old broadcast before the new one exists

**Decision needed** - the order follows `SPEC.md` §5.4.1.

**Where:** `api/rotate_via_api.py:699-723`.

**Problem.** Step 1 completes the outgoing broadcast; steps 2-3 then
insert and bind the replacement. If insert or bind fails (quota, a 5xx
that outlives the retries, a network fault), the channel is left with no
live broadcast until the external check works through its restart ladder
to `--recover`.

**Proposed change.** Insert the new broadcast (and set its category)
*before* completing the old one, then complete, bind, restart and
transition as now. Only the position of one call moves; a failure at
insert then leaves the existing broadcast untouched.

**Related, no decision needed.** Failed rotations leave broadcasts in
`created`/`ready` that no path ever removes: `sweep_stray_broadcasts`
lists `broadcastStatus="active"` only. On a public channel they
accumulate as "upcoming" entries. Record every inserted id in the state
file and, in the sweep, delete (`liveBroadcasts.delete`) those that are
still `upcoming`, not current, and older than an hour.

## B. Robustness

### B1. USB reset sequencing and path derivation

**Where:** `bin/pigeoncam-watchdog.sh:121-128, 225-235`,
`bin/pigeoncam-usb-reset.sh:25-42, 98-114`.

1. **Reset runs while ffmpeg still holds the device**, and the stream is
   restarted immediately afterwards, before the device has re-enumerated.
   The restarted ffmpeg typically fails on a missing node and relies on
   `Restart=always` ten seconds later. Sequence it explicitly: stop the
   unit, reset, wait for `camera.device` to reappear (`udevadm settle`,
   then poll up to about 20 s), start the unit.
2. **`derive_usb_path` fails when the device node is missing**, which is
   the situation most likely to need the reset; only `uhubctl` then
   remains. Cache the derived path in a durable marker on every
   successful stream start and fall back to the cached value.
3. `try_uhubctl` trusts the exit status alone; confirm afterwards that the
   device node exists and say so in the escalation message.

### B2. Oneshot units have no upper bound on run time

**Where:** `systemd/pigeoncam-watchdog.service`,
`pigeoncam-status-check.service` (no `TimeoutStartSec=`, which for
`Type=oneshot` means unlimited), `pigeoncam-rotate.service`
(`TimeoutStartSec=0`, explicitly unlimited).

**Problem.** A timer does not re-fire while its service is still
activating. One hung child (a blocked `systemctl`, an API call stuck in a
retry path) silently stops that health layer for good; `OnFailure=` never
fires because nothing failed.

**Proposed fix.** `TimeoutStartSec=` of 120 s (watchdog), 600 s
(status-check), 1800 s (rotate), 60 s (failure-notify). Assert in
`tests/test_systemd_units.sh` that every oneshot unit sets a finite value.

### B3. Several helpers are only safe because of where they are called from

**Where:** `bin/pigeoncam-status-check.sh:135`
(`media_url=$(resolve_live_media_url ...)`), `lib/pigeoncam-common.sh:757-760`
(pipeline ending in `head`), `:828-830` (`res_token=$(grep | grep | head)`,
`crop_token=$(grep | tail)`).

**Problem.** Each is the bare-assignment-of-a-failing-pipeline shape that
[INCIDENTS.md](INCIDENTS.md) documents as having killed the watchdog
twice. They do not kill the status check today only because
`check_frame_freeze` is invoked as `if check_frame_freeze`, which
suspends `set -e` for the whole call tree. Moving that call out of the
`if` would reintroduce the incident.

**Proposed fix.** Guard each assignment explicitly (`|| true` or
`|| return 0`) so correctness does not depend on the call site. Consider a
lint in `tests/test_err_trap.sh` that flags unguarded `name=$(... | ...)`
lines in `bin/` and `lib/`, with an inline opt-out comment.

### B4. Doctor validates presence, not values

**Where:** `bin/pigeoncam-doctor.sh` (no value checks),
`bin/pigeoncam-setup.sh:880-884` (format, resolution and frame rate asked
with no validator).

**Problem.** Wrong-but-present values fail far from their cause:

- `archive.daytime_start: "4:00"` - `hour_in_daytime` compares strings, so
  a time that is not zero-padded sorts wrongly and silently inverts the
  window.
- `camera.framerate: 29.97` - `$(( framerate * 2 ))` in
  `pigeoncam-stream.sh:198` aborts the service on every start.
- `watchdog.stall_timeout_seconds` at or below the check interval,
  `grace_period_after_rotation_seconds` at or below `min_gap_seconds`,
  `encode.maxrate_kbps` different from `bitrate_kbps` with `cbr: true`.
- Typos in `audio.mode`, `youtube.rotation.mode`, `rotation.schedule`,
  `archive.daytime_mode`, `usb_reset.method` (the last silently means
  "full chain").

**Proposed fix.** One `check_config_values` in the doctor driven by a
table: key, type (`int`, `number`, `enum:a|b|c`, `hhmm`, `WxH`,
`duration`), optional range; plus the cross-field relations above. FAIL
for values a script would crash on or silently misread, WARN for the
relations. Reuse the same validators in the setup wizard.

### B5. The archive can stop silently

**Where:** `bin/pigeoncam-stream.sh:226` (`onfail=ignore` on the segment
output), `bin/pigeoncam-doctor.sh:362-402` (disk space checked only when a
person runs the doctor).

**Problem.** The design keeps the stream alive when the archive output
fails, which is right. But nothing then reports that recording stopped: a
full disk, an unmounted drive or a permissions change ends local
recording with no alert. This is the "how would we know if this stopped
working?" rule from [ORIENTATION.md](ORIENTATION.md), not yet applied to
the archive.

**Proposed fix.**

1. In `pigeoncam-archive-trim.sh` (hourly, already walks the directory):
   if archiving is enabled, the stream unit is active, and the newest
   segment's mtime is older than `segment_length_seconds + 300`, call
   `notify_escalation ARCHIVE_STALLED`.
2. In the same run, `notify_escalation ARCHIVE_DISK_LOW` when free space
   falls below about two days of `daily_archive_gb`.
3. **Decision needed:** an optional retention cap
   (`archive.max_age_days`, default empty = off). The spec deliberately
   declines to enforce a storage budget, so this must stay opt-in.

### B6. Doctor gaps: notification path, clock, credentials, runtime state

1. **`notify_command` empty is not reported.** Every alert in the project
   ends in that command, and the wizard itself notes that a full season
   ran without it. Add a WARN when it is empty and a
   `pigeoncam-doctor.sh --test-notify` that sends a labelled test message
   through `notify_escalation`.
2. **Clock.** Solar scheduling, rotation age and grace windows all depend
   on a correct clock. WARN when `timedatectl show -p NTPSynchronized
   --value` is not `yes`.
3. **API credentials are checked for existence, not validity.** Add a
   `--check` mode to `rotate_via_api.py` (refresh the token, then
   `liveStreams.list(id=persistent_stream_id)`, one quota unit; the helper
   `_check_stream_visibility` already exists) and call it from
   `check_youtube_api`. An expired refresh token is the field-confirmed
   cause of the longest outage on record.
4. **No runtime view.** The doctor is a pre-flight check. Extend
   `pigeoncam-ctl.sh status` with: age of the last successful rotation and
   current broadcast id, age of the newest progress write and newest
   archive segment, the two state files' counters, and each timer's last
   trigger time.
5. Small: `check_stream_key` and the token check require mode exactly
   `600` and reject the stricter `400`; test for "no group/other bits".
   `check_external_check_tooling` hardcodes a 30 s timeout instead of
   `external_check.yt_dlp_timeout_seconds`.

### B7. Setup wizard can write a corrupt line

**Where:** `bin/pigeoncam-setup.sh:204-241` (`render_new_line`).

**Evidence (verified)** by calling the function directly:

| Existing line | New value | Result |
|---|---|---|
| `notify_command: "curl -d \"a\" https://x/#chan"   # hook` | `new cmd` | `notify_command: "new cmd" #chan"   # hook` |
| `notify_command: 'curl -s https://x'` | `curl -d {"a": 1} http://y #z` | `notify_command: curl -d {"a": 1} http://y #z` (unquoted; ` #z` becomes a comment) |
| `  device: /dev/pigeoncam   # c` | `/dev/my cam: x` | `  device: /dev/my cam: x # c` (invalid YAML) |

Causes: the double-quoted pattern stops at the first `"` and does not
understand `\"`, so a second run over a value the wizard itself escaped
mis-splits the line; single-quoted values are not recognised; a bare
original value is replaced by a bare new value whatever it contains.

**Proposed fix.**

1. Parse double-quoted scalars with escape awareness and add a
   single-quoted case.
2. When the original was bare, write the new value bare only if it
   matches a conservative pattern (`^[A-Za-z0-9_./@:+-]+$` with no `: `
   and no ` #`); otherwise double-quote it.
3. A generic safety net after `apply_edits`: re-read every edited key
   through `cfg` and compare with the intended value; on any mismatch
   restore the backup and exit non-zero.

**Tests.** The three rows above, plus a run-twice idempotence test for a
`notify_command` containing both `"` and `#`.

### B8. yt-dlp self-update has no smoke test or rollback

**Where:** `bin/pigeoncam-ytdlp-update.sh`.

A broken upstream release replaces a working binary and takes the
external check down until a person intervenes. Copy the current binary to
`yt-dlp.prev` before `-U`; afterwards run `yt-dlp --version` and, when
`channel_live_url` is configured, one extraction (accepting the not-live
outcomes from [A3](#a3-channel-not-live-is-probably-classified-as-indeterminate));
on failure restore the previous binary and notify.

### B9. Wall-clock markers and clock steps

**Where:** `lib/pigeoncam-common.sh:331-349`.

Markers store `date +%s`. A backwards step yields a negative age that
satisfies every `age < grace` comparison until the clock catches up; a
forward step makes a fresh rotation look overdue. Low probability on a PC
with a battery-backed clock, real on boards without one. Treat a negative
age as "unknown" (the existing large sentinel), and add
`After=time-sync.target` to the rotate and status-check services.

## C. Security and hardening

### C1. Remote content is parsed and decoded as root

**Where:** every `yt-dlp` and network-facing `ffmpeg` invocation in
`lib/pigeoncam-common.sh` (`fetch_live_json`, `resolve_live_media_url`,
`frame_hash_from_url`, `frame_border_from_url`), and
`bin/pigeoncam-ytdlp-update.sh`.

**Problem.** The units run as root by requirement. Within them, a binary
that replaces itself daily from GitHub is executed as root, parses
attacker-influenceable web content, and ffmpeg decodes remote media as
root. None of these needs any privilege beyond network access.

**Proposed fix.** Keep the units as they are and drop privileges per
call, behind one helper in the lib:

```bash
run_unprivileged() { setpriv --reuid=nobody --regid=nogroup --clear-groups --no-new-privs -- "$@"; }
```

`setpriv` is in util-linux. Fall back to a direct call with one WARN when
it is unavailable or the script is not root (tests, manual runs). The
update script itself must stay root to replace the binary, which is one
more reason for [B8](#b8-yt-dlp-self-update-has-no-smoke-test-or-rollback).

### C2. systemd sandboxing can go further, and be measured

The units already carry a good baseline. Additions that fit each unit:

| Unit | Additions |
|---|---|
| all | `UMask=0077`, `ProtectProc=invisible`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6` (plus `AF_NETLINK` where `udevadm` is used), `SystemCallFilter=@system-service` |
| archive-trim | `PrivateNetwork=yes` - unless `notify_command` needs the network, in which case `IPAddressDeny=` is wrong too; document the trade-off |
| stream | `ProtectHome=read-only` (the PulseAudio cookie must stay readable), `DeviceAllow=` for video and sound devices with `DevicePolicy=closed`, `OOMScoreAdjust=-500` |
| ytdlp-update | `ProtectHome=true`, `PrivateDevices=yes` |

Verify each against the real hardware paths (USB reset writes to sysfs and
`/dev/bus/usb`), one unit at a time. Record `systemd-analyze security`
exposure scores in `tests/test_systemd_units.sh` as a ratchet, so a later
edit cannot loosen a unit unnoticed.

### C3. File modes are inconsistent between install paths

1. **`make install` creates `/etc/pigeoncam/config.yaml` mode 0644 in a
   0755 directory** (`Makefile:53-57, 89`; verified on a staged install),
   while `debian/postinst` uses 0640 in a 0750 directory, with a comment
   explaining why. `notify_command` routinely embeds a webhook token. Use
   0750/0640 in the Makefile too, and have the setup wizard create its
   copy and its `.bak-*` files with the same modes.
2. **`_save_token` writes, then chmods** (`api/rotate_via_api.py:250-256`):
   a new token file is briefly created with the process umask, and the
   write is not atomic. Create it with
   `os.open(tmp, O_WRONLY | O_CREAT | O_TRUNC, 0o600)` and `os.replace`.

### C4. State files are sourced as root with unquoted fields

**Where:** `bin/pigeoncam-watchdog.sh:47-59`,
`bin/pigeoncam-status-check.sh:35-68`.

`read_state` sources the state file; `write_state` emits several fields
with `%s`. Today every such field is constrained to digits, hex or
`[0-9.:]` by the code that produces it, so this is not exploitable, but
the safety rests on regular expressions elsewhere. Write every string
field with `%q`, or parse `key=value` lines without evaluating them. See
[F2](#f2-shared-state-file-helper-with-atomic-writes) for the shared
helper.

## D. Installation and packaging

### D1. `make install` fails on the README's own quickstart path

**Where:** `Makefile:58-70`, `README.md` Quickstart steps 2 and 5.

**Problem.** The README says to clone into `/opt/PigeonCamSteward` and
then run `cd /opt/PigeonCamSteward && sudo make install`. The default

**Evidence (verified)** with a checkout installed onto itself:

install: 'bin/pigeoncam-rotate.sh' and '.../bin/pigeoncam-rotate.sh' are the same file

`tests/test_makefile.sh` using a temporary copy of the tree.

### D2. `lib/pigeoncam-usbreset.py` is never installed

**Evidence (verified):** a staged install's `lib/` holds only the two

**Proposed fix.** Install `lib/*.py` as well and add `python3` to
`Depends:` in `debian/control` (it arrives transitively through `yq`

`git ls-files bin lib api tools` must exist in the staged tree.

## E. Tests and tooling

### E1. No continuous integration, and lint skips are silent

**Evidence (verified):** there is no `.github/` directory, and in an
environment without `shellcheck` the suite prints `SKIP` and still ends
"All automated checks passed".

**Proposed fix.**

- A GitHub Actions workflow on push and pull request: Debian or Ubuntu
  runner, `apt install ffmpeg v4l-utils jq yq shellcheck systemd`,
  `pip install ruff flake8`, then `tests/run_all.sh`.
- A second job: `dpkg-buildpackage -us -uc -b`, `lintian`, install the
  `.deb` in a container and run the completeness test from
  [D2](#d2-libpigeoncam-usbresetpy-is-never-installed).
- `PIGEONCAM_CI=1` turns every `SKIP` into a failure, including the two in
  `tests/test_youtube_api.sh` when the venv cannot be provisioned.
- Print a count of skipped checks in the `run_all.sh` summary, so a local
  green run says what it did not cover.

### E2. Two fakes model states the real system cannot produce

The project's own rule is that a fake must not let a test pass against
behaviour the real tool does not have. Two exceptions were found, each
hiding a defect:

1. `tests/test_watchdog.sh` writes a stale progress file after a
   "restart" that the real service would have truncated
   ([A1](#a1-the-usb-reset-escalation-cannot-be-reached)).
2. The fake `yt-dlp`'s `not_live` mode returns JSON with exit 0, which the
   real tool most likely never does for a channel that is not live
   ([A3](#a3-channel-not-live-is-probably-classified-as-indeterminate)).

Beyond fixing both: add a short "fidelity" section to
[ORIENTATION.md](ORIENTATION.md) requiring that each fake mode cite where
its output was recorded from, and audit the remaining fakes (`ffmpeg`,
`v4l2-ctl`, `uhubctl`, `udevadm`) against that rule.

## F. Performance and maintainability

### F1. Load the configuration once per process

**Where:** `lib/pigeoncam-common.sh:263-278` (`cfg`).

**Measured:** ten `yq -r` reads take 0.98 s; ten `jq -r` reads of an
already-converted JSON string take 0.03 s - about 98 ms against 3 ms per
read, on a fast machine. The watchdog makes at least 8 reads every 30
seconds, the status check about 20 per poll, the stream start 27, the
doctor more than 34. Each is a Python interpreter start. The README
targets "modest or older" hardware, and ORIENTATION attributes the
suite's several-minute run time to this.

**Proposed design.**

- `cfg_load`: runs `yq . "$PIGEONCAM_CONFIG"` once, stores the JSON in a
  shell variable (subshells inherit it, so `$(cfg ...)` keeps working) and
  remembers the path it was loaded from.
- `cfg`: if the cache is empty or `PIGEONCAM_CONFIG` differs from the
  remembered path, fall back to the current direct `yq` call. This keeps
  the doctor's `--config` override and the setup wizard (which reads,
  then rewrites, the file) correct without special cases.
- Call `cfg_load` at the top of each script's `main`. A parse failure
  there becomes a single fatal error with yq's real stderr attached.
  Today that stderr is discarded (`2>/dev/null`), a missing `yq` is
  reported as "invalid YAML or filter?", and `exit 1` inside `$(...)`
  only ends the subshell, so a broken config degrades `if cfg_bool ...`
  tests to their defaults.

"Every invocation re-reads config.yaml" remains true: the cache lives for
one process.

**Tests.** Existing suites cover behaviour. Add one asserting a script run
invokes `yq` exactly once (a counting wrapper on `PATH`).

### F2. Shared state-file helper with atomic writes

`read_state`/`write_state` are duplicated in the watchdog and the status
check, write in place (a crash mid-write leaves a truncated file that is
then sourced), and mix `%q`, `%d` and `%s`. Move to the lib:
`state_save <path> <var>...` writing every field with `%q` to a temporary
file followed by `mv`, and `state_load <path>`. Resolves
[C4](#c4-state-files-are-sourced-as-root-with-unquoted-fields) and
simplifies [A6](#a6-status-check-loses-state-on-the-backoff-exit-path).

### F3. Timer intervals duplicated between units and config

**Decision needed.** `watchdog.check_interval_seconds` and
`external_check.poll_interval_seconds` exist both in `config.yaml` and as
`OnUnitActiveSec=` in two timer files; the doctor detects drift. The
rotation timer already uses a cleaner pattern: a fixed short cadence, with
the script deciding whether to act. Applying that to the status check
(timer every 60 s, script returns unless `poll_interval_seconds` has
elapsed since its last poll) removes the duplication and the doctor check
with it, at the cost of a few more process starts - cheap once
[F1](#f1-load-the-configuration-once-per-process) is in. The watchdog's
interval can simply become a property of the unit, with the config key
removed.

### F4. The camera-side frozen-picture check is dead code as shipped

`watchdog.frame_freeze` is marked known-harmful and off, yet its ffmpeg
output, config block, watchdog code and tests remain.
`design/frame-freeze-from-segments.md` specifies the replacement and is
"specified, not implemented". Implement that design and delete the
in-process snapshot output, or delete the feature until then; carrying
both is the worst option. If the in-process route is kept for
experiments, the cheapest test of the documented suspicion is a
`-thread_queue_size` on the audio input (`bin/pigeoncam-stream.sh:156`).

### F5. Research items

Not ready to implement; each needs an experiment first.

1. **API rotation without restarting ffmpeg.** In api mode the broadcast
   boundary is set by API calls, so the encoder restart may be
   unnecessary; skipping it would remove the stream gap and the split
   archive segment at every rotation. The spec requires the restart, so
   this needs both an experiment on a test channel and a maintainer
   decision.
2. **Comment volume.** In `lib/pigeoncam-common.sh` commentary outweighs
   code, much of it incident narrative that also lives in
   [INCIDENTS.md](INCIDENTS.md). The rationale is valuable; its placement
   makes the control flow hard to follow and the two copies will drift.
   Consider trimming each to a two-line statement of the invariant plus a
   link. This is a judgement about style, and the current density is a
   deliberate choice.
3. **Stream key in ffmpeg's argv.** Acknowledged in the code as accepted.
   It is also written to the journal if ffmpeg echoes its output URL at
   higher log levels; worth one check of what the current build prints.

### M3. Crash loop detection (A2)

Needs: the real units; a camera helps. Unplug the camera, or point
`camera.device` at a missing node, and leave it for five minutes.
Capture, for the fake `systemctl`:

```bash
systemctl show -p NRestarts,ActiveState,SubState pigeoncam-stream.service
```

taken several times across the loop. Expected after the fix: one
`STREAM_CRASH_LOOP` notification, a USB reset when the node is missing,
no notification storm. The `systemctl show` capture alone needs any
systemd machine and a unit that exits immediately - not the live system.

### M4. USB reset sequencing (B1)

Needs: the camera and hub. For each of `uhubctl`, `unbind`, `usbreset`:
run `pigeoncam-usb-reset.sh` by hand with the stream stopped, time the
reappearance of `/dev/pigeoncam`, and confirm the cached USB path matches
the derived one after a reboot. The timings set the wait bound in the
fix.

### M5. Rotation retry against the real API (A4, A9)

Needs: the channel and API credentials. Force a failure at rotation time
(block `googleapis.com` at the firewall for a few minutes, then again
with the token file temporarily replaced by an invalid one). Expected:
retries at the agreed cadence, success once the fault is lifted, the
external check quiet throughout, and no abandoned broadcast left on the
channel.

### M7. Credential probe (B6 part 3)

Needs: API credentials. Run the new `--check` mode with a valid token, a
revoked one, and the wrong Google account; confirm three distinct
messages and a quota cost of one unit in the Cloud console.

### M9. Archive stall alert (B5)

Needs: the real stream writing segments. Remount the archive filesystem
read-only, or fill it; confirm the stream continues, and that
`ARCHIVE_STALLED` arrives within the hour. The logic itself is testable
offline with a temporary directory.

### M10. Sandbox directives (C2)

Needs: the full deployment, including real audio mode if used. Apply the
directives one unit at a time and exercise that unit's whole job - a
rotation, a USB reset, a trim, a yt-dlp update - before moving to the
next. A directive that breaks only the rare path is the expected failure.

## Suggested order of work

Arranged so that everything in phases 1 to 4 can be done now, with no
live system. Model suggestions follow one rule: the cheapest model that
is safe for the task, where "safe" depends on how much of the design is
already fixed in this document, how many files and invariants the change
crosses, and how subtle the failure would be if it went wrong. This
codebase penalises shallow shell reasoning - four of its recorded
incidents are `set -e` subtleties - so anything touching control flow in
`bin/` or `lib/` leans towards the stronger model.

| Model | Use it when |
|---|---|
| **Sonnet 5.5** | The fix is specified here, confined to one or two files, and a test can prove it. The bulk of the backlog. |
| **Opus 5.5** | The change redesigns a state machine, crosses several scripts, alters what the system does to real hardware or a real channel, or needs judgement this document leaves open. |
| **Haiku 5.5** | Text-only edits with no behaviour. |

Whichever model implements, have a different session review any change
to the watchdog, the status check or rotation before merging: an
independent reading found the two test-fidelity defects in [E2](#e2-two-fakes-model-states-the-real-system-cannot-produce) that the
authoring sessions could not see.
